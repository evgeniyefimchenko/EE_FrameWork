# ИИ-настройки

В EE_FrameWork есть административный контур для хранения профилей подключения к ИИ-провайдерам. Он нужен, чтобы проект мог подключать разные API без жёсткой прошивки ключей, URL и моделей в коде.

Текущий статус подсистемы:

- профили провайдеров создаются и редактируются в админке;
- API-ключи сохраняются в зашифрованном виде;
- настройки провайдера подгружаются через AJAX при смене select box;
- модель выбирается через поле с поиском и `datalist`;
- подключение можно проверить после сохранения профиля;
- страница статистики пока показывает базовую сводку, журнал вызовов будет подключаться позже.

## Административные маршруты

Основные страницы:

```text
/admin/ai_profiles
/admin/ai_profile/id/<profile_id>
/admin/ai_statistics
```

AJAX endpoints:

```text
/admin/ajax_ai_provider_settings
/admin/ajax_ai_models
/admin/ajax_ai_profile_test/id/<profile_id>
```

Доступ к разделу ограничен ролью администратора.

## Что хранит профиль

Один профиль описывает подключение к одному провайдеру.

Обязательные и основные поля:

- `name` — человекочитаемое название;
- `profile_code` — стабильный код профиля для будущего runtime-использования;
- `provider` — код провайдера;
- `api_base_url` — базовый URL API;
- `model` — выбранная модель или вручную введённый slug;
- `enabled` — включён/выключен;
- `encrypted_api_key` — зашифрованный ключ;
- `api_key_mask` — безопасная маска ключа для UI;
- `settings_json` — provider-specific параметры;
- `last_test_at`, `last_test_ok`, `last_test_message` — результат последней проверки.

Таблица:

```text
ee_ai_profiles
```

`profile_code` уникален. Используйте латиницу, цифры, дефис или подчёркивание.

## Поддерживаемые провайдеры

Сейчас в UI доступны:

- `openrouter` — OpenRouter;
- `openai` — OpenAI;
- `yandex_cloud` — Yandex Cloud AI Studio;
- `sbercloud` — SberCloud / GigaChat;
- `vk_cloud` — VK Cloud.

Все провайдеры используют модель “профиль + базовый URL + ключ + модель”. Различаются только дополнительные поля и способ получения списка моделей.

## OpenRouter

Default base URL:

```text
https://openrouter.ai/api/v1
```

Ключ передаётся как Bearer token. Список моделей запрашивается через:

```text
<api_base_url>/models
```

## OpenAI

Default base URL:

```text
https://api.openai.com/v1
```

Для списка моделей нужен API key. Ключ передаётся как Bearer token.

## Yandex Cloud AI Studio

Default base URL:

```text
https://ai.api.cloud.yandex.net/v1
```

Дополнительное поле:

- `folder_id` — используется для fallback-моделей вида `gpt://<folder_ID>/<model>`.

Ключ передаётся как Bearer token. Если список моделей не удалось получить, UI может показать fallback-варианты с URI, собранными из `folder_id`.

## SberCloud / GigaChat

Default base URL:

```text
https://gigachat.devices.sberbank.ru/api/v1
```

Default OAuth URL:

```text
https://ngw.devices.sberbank.ru:9443/api/v2/oauth
```

Дополнительные поля:

- `oauth_url` — URL получения access token;
- `scope` — один из `GIGACHAT_API_PERS`, `GIGACHAT_API_B2B`, `GIGACHAT_API_CORP`;
- `ssl_verify` — проверять TLS-сертификат при OAuth и models-запросах.

В поле ключа указывается authorization key. Если значение уже начинается с `Basic` или `Bearer`, оно используется как готовый заголовок `Authorization`. Иначе система добавляет `Basic`.

Сначала профиль получает access token через OAuth endpoint, затем запрашивает:

```text
<api_base_url>/models
```

## VK Cloud

Default base URL намеренно пустой, потому что endpoint зависит от проекта.

Укажите OpenAI-compatible endpoint, выданный для вашего проекта. Если endpoint не отдаёт `/models`, в поле модели можно вручную ввести slug модели.

## Поиск и кеш моделей

Поле модели поддерживает быстрый поиск:

- UI отправляет AJAX-запрос в `/admin/ajax_ai_models`;
- сервер запрашивает каталог провайдера;
- результат нормализуется к полям `id`, `name`, `owned_by`, `context_length`;
- список кешируется в `cache/ai/`.

TTL кеша моделей — 24 часа.

Практический вывод: директория `cache/` должна быть доступна на запись web-процессу. Если каталог провайдера временно недоступен, UI может использовать fallback-список или позволить ручной ввод модели.

## Проверка подключения

Проверка доступна только после сохранения профиля, потому что ей нужен `ai_profile_id` и сохранённый ключ.

Тест делает безопасную проверку доступа:

- не запускает генерацию;
- не отправляет пользовательский prompt;
- обращается к models endpoint провайдера;
- сохраняет дату, статус и короткое сообщение в профиле.

Если ключ не задан, проверка возвращает ошибку `api_key_missing`.

## Безопасность ключей

API-ключ не должен попадать:

- в документацию;
- в Git;
- в публичные логи;
- в frontend HTML после сохранения.

При сохранении новый ключ шифруется через `AES-256-GCM` с ключом, производным от `ENV_SECRET_KEY`. В UI показывается только `api_key_mask`.

Если поле ключа оставить пустым при редактировании существующего профиля, сохранённый ключ не меняется.

Если `ENV_SECRET_KEY` не задан, сохранить новый API-ключ нельзя: шифрование должно завершиться ошибкой, а не сохранить секрет в открытом виде.

## Что ещё не является частью runtime

Текущая подсистема — это settings layer. Она уже хранит профили и проверяет доступ к провайдерам, но общий AI Gateway runtime ещё должен быть реализован отдельно.

Пока не следует считать готовыми:

- журнал реальных AI-вызовов;
- подсчёт токенов и стоимости;
- единый сервис генерации;
- retry/rate-limit policy для production-вызовов;
- выбор профиля по бизнес-сценарию.

Эти части должны использовать `profile_code` как стабильную точку подключения, но не должны хранить собственные копии ключей.
